# PLAYBOOKS.md — ขั้นตอนมาตรฐานตามประเภทงาน

ทุก playbook ใช้ร่วมกับ `AGENTS.md` (กฎ R1–R12, Challenge Protocol, รูปแบบรายงาน) เลือกเฉพาะอันที่ตรงกับงาน

## P0 ก่อนเริ่มทุกงาน (1 นาที)
1. จัดประเภทงาน: UI / DB / Edge Function / ประสิทธิภาพ / deploy / CI แดง / เอกสาร
2. `grep -rn "<คำสำคัญ>" docs/CHANGELOG.md docs/BACKLOG.md SUPPLEMENTAL_RULES.md DECISION_LOG.md | head` — เคยทำ/ตัดสินใจเรื่องนี้ไว้หรือยัง
3. ทำ Challenge (AGENTS §3) ก่อนลงมือ — ถ้าแนวคิดมีปัญหา ชี้และเสนอทางเลือก

## P1 ส่งมอบไฟล์ให้เจ้าของ (เจ้าของวางไฟล์ผ่านเว็บ GitHub)
- ตอบเป็นตาราง: `path เต็มจากรากรีโป | ทำอะไร | ใหม่/แก้/ลบ`
- เตือนไฟล์ชื่อซ้ำเสมอ: `app/page.tsx` (ประชาชน) ≠ `app/admin/page.tsx` (แอดมิน)
- ไฟล์ที่ต้องไปด้วยกัน (props/ชนิดข้อมูลข้ามไฟล์) ให้บอกว่า "ต้องวางครบชุดในครั้งเดียว" และชี้ว่าถ้าวางไม่ครบจะเห็น error ไหน
- ลำดับ: **1) SQL (migration) → 2) Edge Function → 3) เว็บ** และบอกว่าแต่ละขั้นข้ามได้หรือไม่ (โค้ดเว็บต้องทนต่อกรณี server ยังไม่อัปเดต)
- แนะนำเสมอ: ใช้ตัวเลือก "Create a new branch" ตอน commit แล้วดูผล CI ก่อน merge (ดู B-003)

## P2 งาน UI / หน้าจอ
1. อ่าน `docs/UI_CONTRACT.md` โดยเฉพาะรายการชื่อที่ e2e อ้างถึง
2. ตรวจที่ 360px (ประชาชน) และ 1280px (แอดมิน) ไม่มี scroll แนวนอน ตัวอักษร ≥ 12px พื้นที่กด ≥ 44px (ประชาชน) / ≥ 40px (แอดมิน)
3. ใช้ส่วนประกอบกลางใน `components/admin/ui.tsx` สำหรับฟอร์มแอดมิน ไม่คิดรูปแบบใหม่ต่อหน้า
4. ครบ 4 สถานะ (Loading/Empty/Error/Success)
5. ค้น `tests/e2e` ด้วยข้อความที่จะเปลี่ยน: `grep -rn "<ข้อความ>" tests/e2e`
6. รายงาน: ภาพรวมที่เปลี่ยน, ไฟล์, สิ่งที่ตรวจที่ 2 ขนาดจอ, สิ่งที่ยังไม่ได้ดูบนเบราว์เซอร์จริง

## P3 งานฐานข้อมูล / RPC
1. ตรวจนิยามจริง: `SELECT pg_get_functiondef('public.<fn>()'::regprocedure);` (ขอให้เจ้าของรัน หรืออ่านผ่าน MCP แบบอ่านอย่างเดียว) — ห้ามเชื่อไฟล์ใน `db/*.sql`
2. เขียน migration ใหม่ idempotent (`IF NOT EXISTS`, `CREATE OR REPLACE`, `DROP TRIGGER IF EXISTS`) พร้อมคอมเมนต์: ทำไม / ผลกระทบ / ย้อนกลับอย่างไร
3. แก้ฟังก์ชันเดิม: **ห่อ (wrapper) ฟังก์ชันใหม่ที่เรียกของเดิม** หรือแพตช์ด้วย `replace` พร้อมตรวจว่ารูปแบบเดิมมีอยู่ ถ้าไม่ตรงให้ `RAISE EXCEPTION` และไม่เปลี่ยนอะไร
4. ผู้ใช้รันเองใน SQL Editor; ห้ามรันบน production ผ่าน MCP (R5)
5. ระบุแผนย้อนกลับ (ลบ trigger/ฟังก์ชัน/คอลัมน์ที่เพิ่ม) และผลต่อเว็บถ้ายังไม่ได้รัน
6. อัปเดต `docs/ARCHITECTURE.md` §3

## P4 งาน Edge Function (`supabase/functions/hdms-api/index.ts`)
1. หยุดถามถ้าจะเพิ่ม action เขียน/ลบ (AGENTS §4, B-001)
2. รักษาความเข้ากันได้สองทาง: เว็บเก่า + function ใหม่ และเว็บใหม่ + function เก่า (ตัวอย่าง: `light`, `getPublicSystemDataAction` ที่ย้อนไปใช้ของเดิม)
3. ไม่รับชื่อตาราง/RPC จากเบราว์เซอร์ ตรวจรูปแบบข้อมูลทุกตัวที่รับ
4. ตรวจไวยากรณ์ได้เองด้วย TypeScript transpile; ทดสอบจริงต้อง `supabase functions deploy hdms-api` (เจ้าของทำ)
5. ย้อนกลับ: deploy เวอร์ชันก่อนหน้า (เก็บไฟล์เดิมไว้ใน git)

## P5 งานประสิทธิภาพ
1. **วัดก่อน** (ตัวเลข): ขนาด response `hdms-api`, จำนวน `<canvas>` ใน overlay pane, Performance tab (ฟังก์ชันที่กิน CPU), Memory tab
2. หาต้นเหตุเชิงโครงสร้างก่อน (ขนาดข้อมูล, วาดซ้ำ, leak) ไม่ใช่เพิ่ม cache/memo มั่ว
3. แก้ทีละต้นเหตุ **วัดหลัง** และรายงานตัวเลขเทียบ
4. กฎเฉพาะแผนที่ใน `docs/ARCHITECTURE.md` §5

## P6 Deploy / ย้อนกลับ / ช่วงเกิดเหตุน้ำท่วม
- Deploy ปกติ: push main → `deploy.yml` (lint → typecheck → build:pages → Pages) ดูผลที่ GitHub → Actions
- ช่วงเกิดเหตุ (ข้อมูลประชาชนต้องถูกต้องที่สุด): **ห้ามปล่อยฟีเจอร์ใหม่ที่ไม่ผ่านด่านตรวจ** ถ้าต้องแก้ด่วน ให้แก้ให้เล็กที่สุดและใช้ Re-run/Manual dispatch หลังตรวจ log
- ย้อนกลับเว็บ: `git revert <commit>` แล้ว push (หรือ revert ผ่านหน้า commit ใน GitHub) · ย้อน Edge Function: deploy ไฟล์เวอร์ชันก่อนหน้า · ย้อน SQL: ตามแผนในคอมเมนต์ migration
- ย้อนเว็บและ Edge Function **พร้อมกัน** ถ้าสัญญา API เปลี่ยน

## P7 CI แดง (วิธีอ่าน log)
1. เปิดขั้นที่แดง หาบรรทัด `path:line:col error` — **ไฟล์ในข้อความ error คือไฟล์ที่ผิดจริง** ไม่ใช่ไฟล์ที่เพิ่ง commit เสมอไป
2. เทียบ `git log -- <path>` ว่าไฟล์นั้นถูกแก้ใน commit ไหน (ตัวอย่างจริง: parse error ที่ `app/page.tsx` เพราะวางไฟล์ผิดที่ ทำให้ build แดงต่อเนื่อง 3 รอบ ขณะที่ไฟล์ที่ส่งไปจริงไม่มีปัญหา)
3. ถ้ายังหาไม่เจอ ให้ revert commit ล่าสุดเพื่อให้ main กลับมาเขียวก่อน แล้วค่อยหาสาเหตุ
4. error อื่นที่ถูกบัง: lint แดงจะหยุด typecheck/build ต่อ แก้แล้วอาจเจอ error ลำดับถัดไป ให้เตือนเจ้าของล่วงหน้า

## P8 งานเอกสาร/กฎ
- แก้เอกสารเมื่อโค้ดเปลี่ยนในงานเดียวกัน ไม่ปล่อยให้เก่า
- เพิ่มกฎใหม่ใน `AGENTS.md` เท่านั้น (ไฟล์ตัวชี้ไม่เพิ่มกฎ) และต้องมีเหตุผลหรือเหตุการณ์ที่ทำให้ต้องมีกฎนั้น
- ประวัติการทำงานลง `docs/CHANGELOG.md` (แบบสั้น) ไม่เพิ่มใน `SUPPLEMENTAL_RULES.md` อีก
