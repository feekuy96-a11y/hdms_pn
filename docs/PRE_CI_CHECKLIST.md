# เช็กลิสต์ HDMS ก่อนส่งเข้า CI

ใช้ร่วมกับ [AGENTS.md](../AGENTS.md) และ [CODEBASE_MAP.md](CODEBASE_MAP.md) เพื่อจับข้อผิดพลาดในเครื่องก่อนส่ง GitHub ไม่ใช่เพื่อข้าม CI ใช้เฉพาะรายการที่เกี่ยวกับงานจริง และบันทึกเหตุผลของข้อที่ไม่เกี่ยวข้อง

## 1. ก่อนแก้: ระบุว่าอะไรต้องผ่าน

- [ ] ตรวจ branch, diff และรุ่นล่าสุดของ `main` อ่านกฎเฉพาะส่วน หากแก้บั๊กให้ลองทำซ้ำบนรุ่นก่อนแก้ด้วยข้อมูลทดสอบ
- [ ] เขียนผลที่ผู้ใช้ต้องเห็นให้ตรวจได้: *จุดเริ่ม → สิ่งที่กดหรือกรอก → ผลที่คาด* รวมเคสผิดพลาดที่เกี่ยวข้องและสิ่งที่ต้องคงเดิม
- [ ] ไล่การเชื่อมต่อ **หน้าหรือปุ่ม → handler/โมดูล → ข้อมูลหรือ API → ผลบน UI** ระบุว่าใครเรียกโมดูล ใช้ข้อมูลรูปแบบใด อะไรอาจกระทบอีกหน้า และทดสอบตรงไหน ถ้าแชร์ระหว่างประชาชนกับแอดมิน ให้แยกพฤติกรรมร่วมจากการเชื่อมต่อและปุ่มเฉพาะหน้า
- [ ] เมื่อแตะข้อมูลแผนที่ ให้เช็กหน่วย ลำดับพิกัด `[lon, lat]` ความสัมพันธ์ของรหัส การแสดงจุดที่ไม่มีหรือถูกถอน และโหมดอ่านโดยไม่แก้ข้อมูลจริง

## 2. ระหว่างและหลังแก้: ตรวจตามความเสี่ยง

- [ ] ตรวจ `git diff --check`, `npm run check:fast` และ ESLint เฉพาะไฟล์ JS/TS ที่เปลี่ยน งานเอกสารล้วนให้ตรวจลิงก์และชื่อคำสั่งจริง ไม่สร้างผล browser ที่ไม่ได้รัน
- [ ] ถ้าเปลี่ยน dependency, lockfile, config การติดตั้ง หรือพบว่าผลในเครื่องไม่เหมือน CI ให้เทียบ Node กับ `ci.yml` (ตอนจัดทำใช้ Node 24) และใช้ `npm ci` เพื่อตรวจติดตั้งจาก lockfile ใน checkout ที่ไม่กระทบงานอื่น อย่าให้เครื่องมือแก้ lockfile โดยไม่ตั้งใจ ([npm ci](https://docs.npmjs.com/cli/npm-ci/))
- [ ] ถ้าเปลี่ยน runtime ของเว็บ ให้ทดสอบบน static export ไม่ใช่แค่ dev server ใช้ตัวรันของโปรเจกต์เพื่อเลือกเคสและจัดการ build โดยอ่านคำสั่งเฉพาะโมดูลจาก Codebase Map; reuse ได้เฉพาะเมื่อ runner ยืนยันว่า artifact และค่าตั้งต้นตรงกัน ([Next.js static export](https://nextjs.org/docs/app/guides/static-exports))

  ตัวอย่างงานป๊อปอัพหมุดน้ำท่วม:
  ```sh
  npm run test:e2e:local -- --reuse-build tests/e2e/admin-boundaries.spec.ts --grep 'does not block.*admin' --workers=1
  ```

- [ ] ทดสอบพฤติกรรมร่วมแบบละเอียดหนึ่งครั้งต่อโปรไฟล์เบราว์เซอร์ที่เกี่ยวข้อง และกดตรวจสั้น ๆ ทั้งสองหน้าที่ใช้จริง รวมปุ่มเฉพาะหน้า มือถือ หรือธีมเมื่อการเปลี่ยนแปลงเสี่ยงถึงส่วนเหล่านั้น
- [ ] ใช้ผลที่ผู้ใช้เห็นเป็นตัวตัดสิน เช่น ป๊อปอัพเปิดและเป็นรายการที่กด ไม่ใช่เพียงปุ่มมีอยู่ ใช้ locator ตามชื่อหรือบทบาท และ assertion ที่รอผลจริง แทนการหน่วงเวลาคงที่ ([Playwright best practices](https://playwright.dev/docs/best-practices))
- [ ] ถ้าผ่านบ้างตกบ้าง ให้เก็บ trace และเทียบตัวอย่างข้อมูล viewport เบราว์เซอร์ จำนวน workers และ build กับ CI; รันซ้ำเฉพาะเคสด้วย `--repeat-each` เพื่อพิสูจน์อาการ เปรียบเทียบรุ่นก่อนแก้กับรุ่นแก้โดยใช้เงื่อนไขเดียวกัน ไม่แก้ด้วยการเพิ่ม retry หรือปิด assertion ([Playwright Trace Viewer](https://playwright.dev/docs/trace-viewer-intro))

## 3. ก่อน merge / ขึ้นเว็บจริง: ใช้หลักฐานจากรุ่นที่จะปล่อย

- [ ] สำหรับการเปลี่ยนโค้ดเว็บ ให้ `npm run check:deploy` ผ่านก่อนส่ง PR ตาม AGENTS และบันทึกคำสั่ง ผลผ่าน/ตก/ข้าม เหตุผล และข้อที่ยังไม่ยืนยัน
- [ ] ตรวจ CI ของ commit ล่าสุดที่ GitHub ใช้ตัดสิน PR: ทั้งสองชุด browser และขั้น offline opt-in/rollback ในชุด 1 ต้องผ่านจริง พร้อมผลรวม `verify` อย่าใช้ผลสีเขียวของ SHA รุ่นเก่าแทน และอย่าปิดด่านเพราะในเครื่องผ่าน ([GitHub required checks](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks))
- [ ] เมื่อได้รับอนุญาตให้ปล่อย ให้ยืนยัน Pages ของ commit บน `main` แล้วลองเฉพาะเส้นทางผู้ใช้ที่แก้บนเว็บจริงแบบไม่เปลี่ยนข้อมูล หากมีปัญหาให้ระบุผลกระทบและวิธีย้อนกลับตาม [Playbooks](PLAYBOOKS.md#p6-deploy--ย้อนกลับ--ช่วงเกิดเหตุน้ำท่วม)

บันทึกสั้นก่อนส่ง: **จุดที่แก้ / ผลที่คาด / คำสั่งและรุ่นที่ใช้ / ผลจริง / ยังไม่ยืนยัน / ลิงก์ CI หรือ trace ที่เกี่ยวข้อง**
