## 1. หลักการ
| | หน้าประชาชน `app/page.tsx` | หน้าแอดมิน `app/admin/page.tsx` |
|---|---|---|
| อุปกรณ์หลัก | มือถือ 360–430px (ออกแบบจากมือถือก่อน) | คอมพิวเตอร์ ≥ 1024px (ออกแบบจากเดสก์ท็อปก่อน) |
| งานหลัก | รู้ว่า "ถนนไหนผ่านได้ไหม" และ "ไปทางไหนแทน" ใน 5 วินาที | กรอก/แก้ข้อมูลถูกต้องและเร็ว ไม่พลาด |
| ลำดับข้อมูล | สถานะ → ระดับน้ำ → ทางเลี่ยง → รูป → ประวัติ | หัวข้อ/ขั้นตอน → ช่องกรอก → ปุ่มหลัก |
| พื้นที่กด | ≥ 44×44px | ≥ 40px สูง |
| ตัวอักษรอ่านจริง | ≥ 12px (ตัวหลัก 14px ขึ้นไป) | ≥ 12px (ช่องกรอก 14px) |

ตัวเลือกทั่วไป: ไม่ใช้สีอย่างเดียวบอกสถานะ (ต้องมีไอคอน/ข้อความ), โฟกัสคีย์บอร์ดมองเห็นชัด, รองรับ `prefers-reduced-motion`, ทุกจอมี Loading/Empty/Error/Success

## 2. โทเค็นและส่วนประกอบกลาง
- `app/hdms-theme.css` เป็นโมดูลหลักของสี: ใช้โทเค็นตามหน้าที่ เช่น `--bg-card`, `--text-primary`, `--state-selected` และ `--focus-ring` ร่วมกันระหว่างประชาชนและแอดมิน ห้ามใส่สีใหม่ในคอมโพเนนต์โดยตรง
- `app/hdms-popup.css` เป็นกรอบร่วม: ใช้ `data-hdms-popup="panel"` สำหรับหน้าต่างทั่วไป, `photo` สำหรับภาพเต็มจอ, `print` สำหรับกรอบเอกสารราชการ และ `hdms-popup-map` ผ่านตัวเชื่อม Leaflet เนื้อหา การเลื่อน และการคืนโฟกัสอยู่กับโมดูลย่อยเดิม เอกสารพิมพ์คงพื้นกระดาษขาว
- แผนที่ฐานและการใช้ธีมมีข้อกำหนดเดียวใน §8 Rule 8; อย่าใช้กติกาลดความสว่างจากเอกสารเก่า
- ใช้ `TRAFFIC_ACCENT` เป็นแหล่งสีเน้นเดียวสำหรับป้าย/ตัวกรองและหมุด/เส้นฝั่งประชาชน ใช้ข้อความและรูปทรงควบคู่สี แยกหน้าที่จากสีพื้นหรือสีข้อความที่เลือกเพื่อคอนทราสต์ สีที่ตั้งไว้ในเครื่องมือจัดการเส้นของแอดมินยังเก็บและแก้ไขได้
- `app/globals.css`: `.doh-readable` (ยกขนาด `text-[10px]`/`text-[11px]` เป็น 12px + วงโฟกัส) ใส่ที่ราก; `.doh-form` (ช่องกรอก ≥ 40px, 14px, มุมโค้งเท่ากัน, caption ของ label) ใส่ที่พื้นที่ฟอร์มแอดมิน
- `components/admin/ui.tsx`: `FormSection` (การ์ดหัวข้อมีเลขขั้น), `ToolGroup` (กลุ่มปุ่มมีป้าย), `ActionButton` (`primary | secondary | pick | danger`, `active`), `StickyActionBar` (แถบบันทึกลอยติดขอบล่าง)
- สถานะจราจร: ใช้ `getTrafficPresentation`, `TRAFFIC_STATUS_OPTIONS` และ `deriveTrafficStatusFromWaterLevel` ใน `lib/traffic-presentation.ts` ชุดเดียวทั้งฝั่งประชาชน แผนที่ และแอดมิน: `PASSABLE` (`ผ่านได้ปกติ`), `LIGHT_VEHICLES_ONLY` (`รถทุกชนิดผ่านได้แต่ไม่สะดวก`), `ONE_LANE` (`รถเล็กผ่านได้ ๑ ช่องทาง`), `WARNING` (`รถเล็กผ่านไม่ได้`), `CLOSED` (`ผ่านไม่ได้`) โดยฟอร์มแอดมินคำนวณสถานะแนะนำอัตโนมัติตามระดับน้ำ (0 / 1–25 / 26–35 ตามส่วนถนน / 36+) และให้แก้ไขเองได้ก่อนบันทึก

## 3. กติกาจัดวางฟอร์มแอดมิน
1. หนึ่งฟอร์ม = หลาย `FormSection` ตามลำดับงานจริง (ข้อมูล → ตำแหน่ง/เส้น → สถานการณ์/ข้อความ) แต่ละการ์ดมีหัวข้อ 1 บรรทัดและคำอธิบายสั้น ไม่เกิน ~7 ช่องต่อการ์ด
2. ปุ่มแบ่ง 3 ระดับ: **หลัก** (หนึ่งปุ่มต่อการ์ด สีเด่น) · **รอง** (กลุ่มด้วย `ToolGroup` ตามหน้าที่) · **อันตราย** (`danger` แยกกลุ่ม และต้องมีขั้นยืนยันถ้าลบข้อมูลถาวร)
3. ปุ่มบันทึก/ยกเลิกของฟอร์มยาวอยู่ใน `StickyActionBar` เสมอ
4. ช่องกรอกทุกช่องมี label ที่เข้าถึงได้ (`<label>` หรือ `aria-label`) ห้ามใช้ placeholder แทน label
5. พื้นที่ฟอร์มรองรับกว้าง ~480–900px: ใช้ `grid-cols-1 sm:grid-cols-2` ไม่ล็อกความกว้างเป็นพิกเซล
6. แถบเครื่องมือเรียงตามความถี่: ปุ่มหลัก → กลุ่มเครื่องมือ → ย้อนกลับ/ล้าง
7. เมนูซ้ายจัดกลุ่มตามงาน เช่น “งานภาคสนาม”, “ข้อมูลแผนที่” และ “ระบบและการส่งข้อมูล”; ชื่อและพฤติกรรมจริงอยู่ที่ [AdminConsole](../components/admin/AdminConsole.tsx)
8. เลือกชนิดตัวควบคุมตามงาน: ตัวเลือกน้อยและต้องเห็นพร้อมกันใช้ปุ่มตัวเลือก; รายการยาวใช้ select หรือช่องค้นหารายการ; ข้อมูลที่ไม่ได้ใช้ในเงื่อนไขนั้นให้ซ่อนและไม่บังคับกรอก
9. งานแผนที่ให้แยกขั้นเลือกวิธี → กำหนดตำแหน่ง → ตรวจหรือปรับแนว → เติมรายละเอียด → สรุปก่อนบันทึก แยกหลัก กม. พื้นที่ และจุดสังเกตของแต่ละหมุด และใช้ปุ่มย้าย A/B ที่กดได้บนมือถือ ไม่พึ่งการลากอย่างเดียว

## 4. หน้าประชาชน (มือถือ)
- รักษาชื่อระบบ/หน่วยงานในหัวเว็บ (`h1`) ให้เห็น ไม่ให้ปุ่มธีมหรือช่องทางติดต่อบังชื่อ มือถือเข้าถึงข้อมูลติดต่อจากเมนูติดต่อได้; ตรวจตามหน้าที่แก้จริง ไม่บังคับแสดงเบอร์ซ้ำทุกขนาดจอ
- แถบล่าง: จำนวนจุดแยกตามสถานะ + ปุ่ม "ดูรายการสายทาง"; รายการสายทางเป็น bottom sheet; รายละเอียดจุดเป็น bottom sheet (`max-h 92dvh`, safe-area)
- รายการเรียงจุดอันตรายก่อน การ์ดเดียว (`FloodCard`) ใช้ร่วมทุกขนาดจอ
- ห้ามมี scroll ซ้อน scroll ในรายละเอียดจุดบนมือถือ

## 5. สัญญากับเทสต์และเทคโนโลยีช่วยการเข้าถึง
**หน้าประชาชน (`smoke.spec.ts`):** `h1` ต้องมีคำว่า "ทางหลวง" · มี `.leaflet-container` · มี `title="ระบบจัดการข้อมูลหลังบ้าน Admin"` · ปุ่มชื่อ "ดูรายการสายทาง" (มือถือ; ต้องมีปุ่มเดียวที่ชื่อนี้) · ช่องค้นหา placeholder มี "ค้นหาสายทาง" · ข้อความ empty-state อยู่ใน `p` หรือ `h4` · ปุ่ม "ล้างตัวกรอง" · dialog ชื่อ "รายละเอียดจุดน้ำท่วม <ชื่อตอน>" · ในรายละเอียด: ข้อความสถานะ (เช่น "รถเล็กผ่านได้ ๑ ช่องทาง"), ชื่อทางเลี่ยงที่ผูก (ข้อความตรงตัว ในอีลิเมนต์เดียว), "อัปเดตล่าสุด:" (ต้องมีอีลิเมนต์เดียว) · ไม่มี scroll แนวนอนที่ 412px

**หน้าแอดมิน (`admin-menus.spec.ts`, `gis-import.spec.ts`):**
- มี `<aside>` (role complementary) **เพียงตัวเดียว** และปุ่มเมนูใน aside ต้องมี accessible name ตามชื่อเมนู: จัดการระบบ, รายการเหตุการณ์, รายการทางเลี่ยง, โครงข่ายสายทาง, โครงการผู้ว่าฯ, จัดการแผนที่, สไตล์เส้นทาง (ปุ่มเมนูมือถือเป็นข้อความ label ล้วน และต้องตรงตัวเมื่อค้นแบบ exact)
- หัวข้อประจำแต่ละเมนู (เมื่อเปิดเมนูแล้วต้องเห็นข้อความนี้): จัดการระบบ → "ข้อมูลทั่วไปและเบอร์โทรฉุกเฉิน" · จัดการแผนที่ → "จัดการแผนที่และรายงานเหตุการณ์" · รายการเหตุการณ์ → "ทะเบียนเหตุการณ์น้ำท่วม" · รายการทางเลี่ยง → "เส้นทางเลี่ยงทั้งหมด" · โครงข่ายสายทาง → "โครงข่ายสายทาง" · สไตล์เส้นทาง → "สตูดิโอปรับแต่งสไตล์เส้น" · โครงการผู้ว่าฯ → "แผนงานโครงการแก้ไขปัญหาน้ำท่วม"
- หัวข้อ/ข้อความ: "ทะเบียนเหตุการณ์น้ำท่วม" (heading), "ปรับแนวถนนทางหลวง" (heading), "บันทึกข้อมูลระบบ", "เพิ่มเหตุการณ์", "วาดทางเลี่ยงใหม่บนแผนที่", "เลือกไฟล์โครงข่ายเส้นทางหลวง", "เพิ่มโครงการใหม่", "นำเข้าแนวเส้นเพื่อแก้รายละเอียดภายหลัง", "บันทึกเป็นฉบับร่าง (ยังไม่แสดงบนแผนที่ประชาชน)" (ตรงตัว), "ตรวจสอบโครงข่ายสำเร็จ", "พบเส้นทาง 1 เส้นในไฟล์"
- ตัวแก้ไขแนวถนน: ปุ่ม "แนวถนน" (exact), **ปุ่มเดียวชื่อ "เกาะแนวถนน"** (ห้ามให้ปุ่มอื่นมีคำนี้ในชื่อ), "คืนค่าแนวเดิม", "ส่งออก GeoJSON", "ส่งออก KML" · ตัวแก้ไขเปิดในโหมด "ตามถนน (OSRM)" เป็นค่าเริ่มต้น

## 8. ระบบสีและกฎภาคสนาม (Core Color System & Field GIS Usability Rules)

### Part 1: Core Color System Rules (กฎหลักระบบสี 6 ข้อ)

#### Rule 1: Zero Hardcoded Hex in Components (แยก Scale ออกจาก Semantic Tokens)
- **ห้าม** เขียนรหัสสี Hex/RGB แบบ Hardcode ลงใน HTML, JSX, JS หรือ CSS ของคอมโพเนนต์โดยตรง
- **ต้อง** ใช้ระบบ 2 ชั้นเสมอ:
  1. **Primitive Scale (`50–950`):** ไล่เฉดสีฐาน (Slate Navy, Deep Teal, Ice Blue, Amber, Red, Orange, Yellow, Cyan, Green)
  2. **Semantic Tokens:** ตั้งชื่อตามหน้าที่ใช้งานจริง (เช่น `--bg-card`, `--text-primary`, `--brand-active`, `--status-danger-bg`) เพื่อให้สลับ Light/Dark Mode ได้จากการเปลี่ยนค่า Token ชุดเดียว

#### Rule 2: Unified Status Color Mapping (Map = Card = Badge = Filter)
สีของสถานะจราจรและภัยพิบัติ **ต้องตรงกัน 100%** ทั้งบนหมุดแผนที่ (Markers), เส้นทางถนน (Polylines), การ์ดสรุปด้านข้าง, ป้ายสถานะ (Badges) และเมนูตัวกรอง (Dropdown):
- **ผ่านไม่ได้ (`status.danger`):** โทนแดง (`Red`)
- **รถเล็กผ่านไม่ได้ / เฝ้าระวัง (`status.warning-high`):** โทนส้ม / อำพันเข้ม (`Orange / Deep Amber`)
- **รถเล็กผ่านได้ 1 ช่องทาง (`status.warning-low`):** โทนเหลือง / ทอง (`Yellow / Gold`)
- **รถทุกชนิดผ่านได้แต่ไม่สะดวก (`status.info`):** โทนฟ้า / ไซแอน (`Cyan / Sky Blue`)
- **ทางเลี่ยง (`route.detour`):** โทนเหลืองอำพันมีขอบ (`Amber / Gold`) — *ต้องแยกโทนให้ชัดจากสีแดงของจุดน้ำท่วม*
- **เส้นทางปกติ / กล้อง CCTV (`status.normal`):** โทนเขียวเข้ม (`Dark Green`)

#### Rule 3: 60·30·10 Visual Balance (คุมสัดส่วนสีไม่ให้แย่งซีนแผนที่)
- **60% พื้นหลังกลาง (Dominant Neutral):** พื้นหลังขาว/เทาอมฟ้าอ่อนมาก (Light) หรือ Slate Navy เข้ม (Dark) สำหรับ Sidebar, ช่องค้นหา และพื้นหลังการ์ด
- **30% โครงสร้างรอง (Secondary):** เส้นขอบบางๆ, ปุ่ม Outlined ใน Header (`ติดต่อ`, `สายด่วน 073-336051`), ชิปข้อมูลประกอบ (`ระดับน้ำ`, `ฝั่งน้ำท่วม`)
- **10% สีเน้นและจุดสำคัญ (Accent & Status):** ใช้เฉพาะแท็บ/ตัวกรองที่ Active อยู่, ข้อความพิกัด/กม., ปุ่มนำทางหลัก (`ดูบน Google Maps`) และป้ายสถานะ

#### Rule 4: WCAG Contrast & Intentional Active Inversion
- ข้อความปกติต้องมีค่า Contrast Ratio อย่างน้อย **4.5:1** และข้อความขนาดใหญ่/ไอคอนอย่างน้อย **3:1**
- **การกลับขั้วสี Active (Active State Inversion):**
  - **Light Mode:** แท็บหรือตัวกรองที่ถูกเลือก (`น้ำท่วม`, `ทุกสายทาง`) ใช้พื้น **Deep Teal** + ตัวอักษร **สีขาว**
  - **Dark Mode:** กลับขั้วเป็นพื้น **Soft Ice Blue** + ตัวอักษร **Slate Navy เข้ม** เพื่อให้อ่านชัดบนพื้นมืด

#### Rule 5: Dark Mode Elevation & Subtle Borders
- พื้นหลังหลัก (`--bg-app`) ต้องเข้มกว่าพื้นหลังการ์ดและช่องค้นหา (`--bg-card`, `--bg-input`) เสมอ
- การ์ดทุกใบใน Dark Mode ต้องมีเส้นขอบบาง `--border-subtle` (โทนเทาอมน้ำเงิน) เพื่อแยกชั้นความลึก ไม่ให้การ์ดจมกลืนไปกับพื้นหลัง

#### Rule 6: Floating Map Controls Over Light Map Tiles
- เนื่องจากแผนที่พื้นหลัง (Longdo / NuMAP) ยังแสดงผลเป็นโทนสว่างแม้ผู้ใช้จะเปิด Dark Mode
- ปุ่มควบคุมที่ลอยอยู่บนแผนที่ทุกชิ้น (`น้ำท่วม X จุด`, `ทางเลี่ยง X เส้นทาง`, ปุ่มซูม `+`/`-`, ปุ่มระบุตำแหน่ง, ปุ่มสลับชั้นข้อมูล) **ห้ามใช้พื้นหลังโปร่งใสจัด** ต้องคงความทึบแสงสูง (`opacity >= 0.92`) และมี `box-shadow` ชัดเจนเสมอ

### Part 2: Field GIS & Usability Rules (กฎเสริมสำหรับงานภาคสนาม 5 ข้อ)

#### Rule 7: Never Rely on Color Alone (Color + Shape / Pattern)
- เนื่องจากสีของ `ทางเลี่ยง`, `รถเล็กผ่านไม่ได้` (ส้ม/อำพัน) และ `รถเล็กผ่านได้ 1 ช่องทาง` (เหลือง/ทอง) อยู่ในตระกูลเดียวกัน การสื่อสารบนแผนที่และป้ายสถานะ **ห้ามใช้สีอย่างเดียว**
- **เส้นทางเลี่ยง (Detour Polylines):** ต้องใช้เส้นประ (`dashArray`) หรือสัญลักษณ์ลูกศรทิศทางควบคู่กับสีเหลืองอำพัน เพื่อแยกจากเส้นน้ำท่วมทึบอย่างชัดเจน
- **หมุดและป้ายสถานะ:** ต้องใช้รูปทรงไอคอนที่ต่างกันตามระดับความรุนแรง (เช่น กากบาท/ห้ามผ่าน, สามเหลี่ยมเตือน, คลื่นน้ำ, ลูกศรเลี่ยง) เพื่อรองรับการดูกลางแดดจ้าและผู้ที่มีภาวะตาบอดสี

#### Rule 8: Basemap unchanged in both themes
- **คงแผนที่ฐานสว่างและสีเดิมทั้ง Light/Dark** ห้ามใส่ CSS filter ที่ tile pane, ตัวแผนที่, Canvas เส้น หรือหมุด ให้สลับเฉพาะพื้นและสีของปุ่มลอย ป้ายและป๊อปอัปผ่านโทเค็น
- ยืนยันจาก [CSS ธีม](../app/hdms-theme.css) และ [เทสต์แผนที่](../tests/e2e/gis-focus-mode.spec.ts) ที่กำหนดให้ชั้นแผนที่ไม่มี filter ข้อนี้แทนคำสั่งเก่าที่ให้ลดความสว่างของ tile pane

#### Rule 9: Explicit Interactive & Focus States
- ต้องกำหนด Token สำหรับสถานะโต้ตอบทุกคอมโพเนนต์ที่กดได้ (`--state-hover`, `--state-selected`, `--focus-ring`)
- เมื่อผู้ใช้คลิกเลือกการ์ดเหตุการณ์ใน Sidebar หรือคลิกหมุดบนแผนที่ การ์ดที่เชื่อมโยงกันต้องเปลี่ยนเป็นสถานะ `--state-selected` (มีพื้นไฮไลต์และขอบเน้น) เพื่อให้รู้ทันทีว่ากำลังดูจุดไหนอยู่

#### Rule 10: Field Typography (`tabular-nums`) & Touch Targets
- ตัวเลขเชิงพื้นที่และข้อมูลเรียลไทม์ทั้งหมด เช่น ช่วง กม. (`กม. 12+400`), ระดับน้ำ (`40 ซม.`), เวลาอัปเดต และตัวนับจำนวนจุดบนปุ่ม **ต้อง** กำหนด `font-variant-numeric: tabular-nums;` เพื่อป้องกันตัวเลขกระตุกหรือขยับแนวนอนเมื่อข้อมูลรีเฟรช
- ปุ่มควบคุมบนแผนที่และปุ่มหลักบนหน้าจอมือถือต้องมีขนาดพื้นที่สัมผัส (Touch Target) ไม่เล็กกว่า **44×44 px** เพื่อความแม่นยำในการกดขณะปฏิบัติงานหรือเดินทาง

#### Rule 11: Data Freshness Visual Hierarchy
- ใช้ [`resolveReportFreshness`](../lib/traffic-presentation.ts) เป็นแหล่งตัดสิน ไม่คำนวณแต่ละหน้าแยกกัน: ใหม่เมื่อไม่เกิน 2 ชม., เริ่มเก่าเมื่อเกิน 2 ถึง 6 ชม., เก่าเมื่อเกิน 6 ชม., ไม่ทราบเมื่อเวลาไม่ถูกต้อง ไม่มี หรืออยู่ในอนาคต
- แยกความสดใหม่ด้วยข้อความและสี อย่ากลบสถานะการผ่านทาง และอย่าแสดงข้อมูลที่ไม่ทราบเป็นข้อมูลใหม่หรือค้างโดยเดา

### Required Semantic Token Structure

ใช้โครงสร้างตัวแปร CSS ต่อไปนี้เป็นมาตรฐานกลาง (ปรับค่า Hex/OKLCH ให้ตรงกับธีมของระบบ):

| Token Name | บทบาทหน้าที่ | Light Mode | Dark Mode |
| :--- | :--- | :--- | :--- |
| `--bg-app` | พื้นหลังหลักของแอป / แถบด้านข้าง | ขาว / เทาอมฟ้าอ่อนมาก | Slate Navy เข้มสุด |
| `--bg-card` | พื้นหลังการ์ดข้อมูลและ Modal | ขาวบริสุทธิ์ | Slate Navy สว่างขึ้น 1 ระดับ |
| `--bg-input` | ช่องค้นหาและ Input | เทาอมฟ้าอ่อน | Slate Navy เข้มกว่า Card เล็กน้อย |
| `--border-subtle` | เส้นขอบการ์ดและปุ่ม Outlined | เทาอมฟ้าจาง | เทาอมน้ำเงินบาง |
| `--text-primary` | ชื่อตอน, หมายเลขทางหลวง, หัวข้อ | กรมท่าเข้ม / เทาเข้ม | ขาว / เทาอ่อนสว่าง |

### Strict Guardrails (ข้อห้ามเด็ดขาด)
1. **ห้าม** ใช้สีแดงสดของสถานะ `ผ่านไม่ได้` กับเส้นทางหรือปุ่ม `ทางเลี่ยง` เด็ดขาด
2. **ห้าม** ใช้สีตัวอักษรที่อ่านยากบนพื้นมืด (เช่น เทาเข้มบนพื้น Slate Navy) ให้ตรวจสอบ Contrast ทุกครั้ง
3. **ห้าม** สร้างปุ่มหรือการ์ดใหม่โดยไม่ผูกกับ Token ในตารางด้านบน
4. **ห้าม** ทำให้ปุ่มลอยบนแผนที่โปร่งใสจนกลืนกับชื่อถนนหรือเส้นทางบน Longdo/NuMAP
5. **ห้าม** ใส่ Filter ลดความสว่างใน Dark Mode ครอบทั้งแผนที่จนทำให้หมุดน้ำท่วมและเส้นทางเลี่ยงมืดตามไปด้วย
6. **ห้าม** ใช้สีเพียงอย่างเดียวในการแยกความแตกต่างของเส้นทางและระดับความรุนแรงบนแผนที่โดยไม่มีรูปทรงไอคอนหรือรูปแบบเส้นประกอบ

### Output & Verification Checklist
ทุกครั้งที่แก้ไขหรือสร้าง UI ใหม่ ให้ตรวจสอบ 7 ข้อนี้ก่อนส่งงานเสมอ:
1. ไม่มี Hardcoded Hex ในไฟล์ Component (เรียกผ่าน CSS Variables ทั้งหมด)
2. สลับ Light Mode ↔ Dark Mode แล้วสี Active Tab, ข้อความ กม., ขอบการ์ด และปุ่มและป๊อปอัปเปลี่ยนตามธีม โดยภาพพื้นแผนที่ หมุด และเส้นไม่ถูกตัวกรองเปลี่ยน
3. สีบนหมุด/เส้นแผนที่ตรงกับสีบนการ์ดสรุปและป้าย Badge พร้อมรูปทรงไอคอน/เส้นประที่แยกได้แม้ไม่ดูสี
4. ปุ่มลอยบนแผนที่ยังคงอ่านชัด มีเงาแยกชั้น และมีขนาด Touch Target ไม่ต่ำกว่า 44×44 px บนมือถือ
5. การคลิกการ์ดหรือหมุดแสดงสถานะ `--state-selected` และรองรับ `--focus-ring` ชัดเจน
6. ตัวเลข กม., ระดับน้ำ และตัวนับจำนวนจุดใช้ `tabular-nums` ไม่กระตุกเมื่ออัปเดต
7. ป้ายเวลาอัปเดตแยกความสดใหม่ของข้อมูล (`fresh` / `stale`) ได้อย่างชัดเจน
